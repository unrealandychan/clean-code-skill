## Workflow 1: Executable Specification Generation (`/gherkin-spec`)

**Trigger**: Before unleashing an AI agent to write production code.

### Step 1: Extract Given-When-Then Scenarios

Transform user intent into unambiguous, executable Gherkin feature files:

```gherkin
Feature: <Feature Name>
  As a <Role>
  I want <Capability>
  So that <Business Value>

  Scenario: <Happy Path Scenario>
    Given <Initial State / Pre-condition>
    When <Action or Event Occurs>
    Then <Expected Observable State Change>
    And <Expected Invariant Preserved>

  Scenario Outline: <Boundary & Edge Case Matrix>
    Given an input with value <InputVal>
    When the processing is triggered
    Then the system returns <ExpectedResult>
    And no unexpected side effects occur

    Examples:
      | InputVal     | ExpectedResult |
      | ""           | ValidationError|
      | -1           | OutOfBounds    |
      | "valid_data" | Success        |
```

### Step 2: Bind to Test Runners

- **Python**: `pytest-bdd` or `behave`
- **TypeScript/JavaScript**: `@cucumber/cucumber` or `jest-cucumber`
- **Java**: `io.cucumber:cucumber-java`
- **Go**: `github.com/cucumber/godog`

## Workflow 2: Pre-Task Constraint Harness Setup (`/vibe-guard`)

**Trigger**: Initializing a repository or workspace for AI-driven vibe coding.

### Checklist

1. **Verify Test Baseline**: Run existing test suite; ensure 100% pass rate.
2. **Verify Linter Baseline**: Run linter; ensure zero errors and zero warnings.
3. **Configure Mutation Runner**: Verify mutation tool is installed and configured.
4. **Lock Invariant Fences**: Ensure domain models and value objects are typed and immutable.

### Tooling Setup Reference

| Language       | Linter & Type Checker               | Test Runner                           | Mutation Testing Tool                          | Complexity / CRAP Tool     |
| :------------- | :---------------------------------- | :------------------------------------ | :--------------------------------------------- | :------------------------- |

## Workflow 3: Mutation Testing Audit (`/mutation-audit`)

**Trigger**: AI agent has generated code and passing unit tests; time to prove the tests can catch real bugs.

### Philosophy

Passing 100% of unit tests means nothing if the tests only assert trivialities. Mutation testing alters operator logic (e.g. changing `>` to `>=`, `+` to `-`, removing function calls) to create "mutants". If a test fails when a mutant is introduced, the mutant is **killed** (good). If tests still pass, the mutant **survived** (test suite failure).

### Execution Commands

#### TypeScript / JavaScript (Stryker)

```bash
# Run Stryker on changed files
npx stryker run --mutate "src/**/*.ts"
```

_Threshold: Mutation Score $\ge 85\%$_

#### Python (mutmut)

```bash
# Run mutmut on target module
mutmut run --paths-to-mutate src/domain/
# Check results
mutmut results
```

_Threshold: Surviving mutants == 0 on new code._

#### Java (PIT / Pitest)

```bash
mvn org.pitest:pitest-maven:mutationCoverage
```

## Workflow 4: Cyclomatic Complexity & CRAP Metric Calculation (`/crap-metric`)

**Trigger**: Auditing code generated by agents for hidden structural complexity and maintenance risk.

### The CRAP Metric Formula

$$\text{CRAP}(m) = \text{comp}(m)^2 \times (1 - \text{cov}(m))^3 + \text{comp}(m)$$
where:

- $\text{comp}(m)$ = Cyclomatic Complexity of method $m$
- $\text{cov}(m)$ = Test code coverage percentage (between 0.0 and 1.0)

### CRAP Threshold Guide

- **$\text{CRAP} \le 15$**: Clean, low-risk, maintainable code.
- **$15 < \text{CRAP} \le 30$**: Moderate risk; acceptable only with comprehensive test coverage.
- **$\text{CRAP} > 30$**: **CRAP Threshold Breach**. Highly risky and unmaintainable. Immediate rejection.

### Execution Commands

#### Python

```bash
# Cyclomatic Complexity (flag functions with complexity > 10)
radon cc src/ -s -a -nb
# CRAP index calculation
radon crap src/ -t 30
```

#### TypeScript / JavaScript

```bash
# Enforce max complexity ≤ 10 via ESLint
npx eslint src/ --rule 'complexity: ["error", 10]'
```
